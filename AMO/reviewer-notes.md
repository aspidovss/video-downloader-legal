# Notes for the AMO reviewer — Video Downloader Legal 1.6.4

**New in 1.6.4 (all local, no new permissions, no remote code):**
* `lib/rate.js` — download speed / time left shown in the popup.
* `lib/ts2mp4.js` `convertTsMkv` + `writeMkvAvcAac` in `lib/mux.js` — MPEG-TS (H.264 + AAC) written as Matroska without re-encoding (the user picks MP4 / MKV / TS).
* `lib/gif.js` (own GIF encoder: median-cut palette, LZW) and `lib/gifvideo.js` — on request, a short video (≤ 60 s) already downloaded by the extension is decoded by a `<video>` element from a `blob:` URL in the background page, frames are drawn to a canvas and encoded as an animated GIF. Off / JoyReactor only (default) / all sites in the options.
* `lib/joyreactor.js` — JoyReactor post files (`img*.joyreactor.*/pics/post/{webm,mp4}/…`) grouped into one entry; the extension's own requests to that image server carry the site's page as `Referer` (the server answers 404 without it), using the same mechanism as below.
* `lib/updatecheck.js` holds only pure helpers (version compare) that the popup and options import; the GitHub release check itself exists only in a separate Chrome / Edge package (`platform/updater.js`, not in this .xpi). The Firefox add-on makes no update-check requests.
* Tests use FFmpeg as an external tool only (see THIRD-PARTY.md); it is not part of the add-on.

**What it does.** Detects media on web pages (direct files, HLS, DASH) and saves it through the browser's downloads API.
It never decrypts or bypasses DRM: DRM-protected streams are detected and refused.
Everything runs locally; no data is sent to the developer or to any analytics service.

**AI disclosure.** The code of this project was generated by AI; all texts, comments, descriptions and translations are AI-generated.

**Source.** The package is plain, unminified JavaScript (ES modules): a zip of the source folders, nothing transpiled or minified (`node scripts/build-amo-dev.mjs --release` or `npm run build`). One third-party file: `vendor/lame.js` = lamejs 1.2.1 (LGPL-3.0, https://github.com/zhuker/lamejs, tag 1.2.1), its unmodified sources bundled into one readable, non-minified file by `scripts/build-lamejs.mjs` (SHA-256 in `vendor/README.md`; rebuild and compare with `node scripts/build-lamejs.mjs`), used only for the optional "Audio only → MP3" conversion; it runs locally and makes no network requests.
`tests/` contains node:test unit tests (`node --test tests/*.test.js`).
Chrome-only code (the offscreen document client, `platform/`) is not in this package: `service/offscreen-client.js` is a stub here, and the Chrome build replaces it with `platform/offscreen-client.js`, so the validator reports no `offscreen.createDocument` warning. `gecko_android.strict_min_version` is 142.0 because `data_collection_permissions` needs Firefox for Android 142; the extension itself is built for desktop Firefox (it uses `sidebar_action`).

## Permissions — why each is needed
| Permission | Why |
|---|---|
| `downloads` | save the detected file |
| `webRequest` | observe media requests (manifests, segments) to list what the page plays |
| `webRequestBlocking` | the extension's own background requests to YouTube/googlevideo must carry a mobile-client `User-Agent`/`Origin`/`Referer`, its own requests to Bilibili's video servers/API must carry the site's `Referer`, and its own requests to TikTok's video/cover hosts (`tiktok.com`, `tiktokcdn*.com`, `ibytedtos.com`, `ibyteimg.com`, `byteimg.com`) must carry `Referer: https://www.tiktok.com/` (the site's player sends it too); page requests are never modified (listener ignores `tabId != -1` and requests not originated by the extension) |
| `webNavigation`, `tabs` | reset per-tab lists on navigation, show the list for the active tab |
| `storage`, `unlimitedStorage` | settings, download history; `unlimitedStorage` for large in-memory/Blob staging while joining segments |
| `notifications` | "download finished / failed" |
| `clipboardWrite` | the "Copy" buttons of the diagnostics panel and of the optional debug log (options) |
| host `<all_urls>` | video sites are not known in advance; content script lists `<video>`/`<source>` elements and sees media requests |

## Content scripts
* `injected/page.js` (all http/https frames): reads `<video>`/`<audio>`/`<source>` URLs and reports them to the background; in the top frame it also reports each `<video>`'s poster address and whether it is on screen (used to match the detected HLS playlists of a feed of short videos to their cover and name, `lib/feed.js`). It does not change the page.
  *Firefox for Android only (new in 1.6.1):* `downloads.download()` never answers there (the downloads API is not connected to the browser's download manager, Mozilla bug 1793214). The background then sends the finished file (a Blob, via `tabs.sendMessage`) to this script in the tab of the video, which saves it with a temporary `<a download>` link to a `blob:` address (not inserted into the page) once the tab is on screen — Firefox shows its normal "Download file?" dialog. No other use; desktop Firefox keeps using the downloads API.
* YouTube only: `injected/youtube_main.js`, `injected/youtube_rec.js` (MAIN world) read the page's player data and, **only when the user presses "Record"**, copy the media segments the player itself appends to its MediaSource so they can be saved. DRM (`encrypted` event) aborts recording.

* TikTok (`injected/tiktok.js` isolated, `injected/tiktok_main.js` MAIN world, tiktok.com only): read-only. The MAIN-world script reads the player's own props (video id, caption, author, cover, play address) to tell which detected file is the video on screen, and posts them to the isolated script via `window.postMessage`, which forwards them to the background. It makes no requests and changes nothing on the page. If the background request is refused by the CDN, the isolated script may fetch the file with the page's own session (`tt_fetch`), as the player does.
* Instagram / Facebook (`injected/instagram.js`, isolated world, top frame): on post/reel/story/video pages it reads the media addresses (DASH manifest, plain mp4 list) from the page's own data (the page HTML fetched with the user's own session, or the DOM) and hands them to the background. Nothing is decrypted or forged.
* X / Twitter (`injected/x.js`): reads `<video>` poster addresses and tweet links to tell which detected video is on screen; no network requests.
* Canva (`injected/canva.js`): reads the HLS address (`hlsManifestUrl`) from the page's inline script on `/watch` pages.
* Bilibili: no content script; the background calls the site's public web API (`api.bilibili.com` view/nav/playurl with the site's standard "wbi" signature, `api.bilibili.tv` playurl) for the page the user is on.
* Vimeo/Dailymotion: public player config endpoints for the page's video.
* Live recording (Twitch and other HLS live streams): the user presses "Record"; new segments of the public playlist are fetched until "Stop". `lib/rebase.js` shifts timestamps so the file starts at 0:00.
* `lib/ts2mp4.js` (new in 1.5.2): own converter MPEG-TS (H.264 + AAC) → MP4 without re-encoding, runs locally on the downloaded bytes; any other codec/stream type is left as TS. No WASM, no remote code.
* HLS media playlists with video and sound as separate playlists and an unreadable master (one-time token): `lib/hlsgroup.js` reads the init segment of each playlist (track type, size, codec) and offers them as one entry; video and sound are recorded side by side and joined into one MP4. Fragmented MP4 results are rewritten as an ordinary MP4 with the index first (`defragMp4` in `lib/mux.js`); only bytes are copied.
* Segments of ordinary (non-DRM) streams are fetched and joined locally (own MP4 / WebM / Matroska muxer in `lib/mux.js`, no remote code, no WASM). Video and audio of different formats (e.g. AV1 + Opus) are written as an ordinary MP4 without re-encoding.
* Servers that refuse the extension's own request (HTTP 403 / 412) but serve the page's player (new in 1.6.4): the extension repeats its own request with the page's address as Referer / Origin (blocking `webRequest`, only requests with `tabId -1` made by this extension, only for that server's domain), and if still refused, asks its content script in that tab to fetch the playlist / piece with the page's own context (`vdl_fetch` in `injected/page.js`); the bytes are returned to the background. Page requests are never modified.
* PornHub watch pages (`lib/sites.js`, `resolvePornhub`, new in 1.6.4): the background reads the page's HTML (the player settings object `flashvars_*`) and the site's own `/video/get_media` list to offer the MP4 file of each quality.
* Firefox for Android 142+: the same package; APIs the phone does not have (commands, notifications, sidebarAction) are guarded and their controls hidden.

## Network
* Requests go to the page's own media hosts and, for YouTube, to `www.youtube.com/youtubei/v1/player` and `www.youtube.com/sw.js_data` (the same bootstrap data any YouTube client uses), `www.youtube.com/api/timedtext` (subtitles, only when the user asks for them) and `*.googlevideo.com`.
* No credentials are forged, no PO tokens or signatures are generated, no player code is executed.

## Data collection
`data_collection_permissions.required = ["none"]`. Nothing leaves the user's browser except requests described above, which go to the sites the user is already watching.

Press **I accept** to continue; **I decline** closes the popup and shows the terms again next time. Until accepted, downloads and the hotkeys are refused. 2. YouTube watch page → "Download" lists formats; "Record" is the fallback.
3. (Optional) Options > Diagnostics > *Debug log* (off by default) keeps a local text log in `storage.local` (links masked); it can be viewed, copied, saved or cleared, never sent by the extension. The 🐞 button runs a short self-test and saves a diagnostics file locally (URLs are masked unless the user enables full URLs in settings); the file is never sent by the extension, the user chooses whether to send it.
